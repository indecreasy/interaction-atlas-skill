# 从应用行为到可执行的地图

以书架和收藏打开同一本书为例：详情页只有一个 ID，却有两个上游。点击返回时，用户应该回到这次打开书的地方。若为每个入口复制详情页，同一个按钮会出现两份定义，之后很容易只改到一份。

## 一份数据，三种读法

| 部件 | 读取什么 | 产出什么 |
| --- | --- | --- |
| 模型 `model.js` | 页面、动作、需求、示例状态和依据链接 | 供其他部件使用的稳定 ID 及关联 |
| 导航 `core.js` | 当前页、进入路径、可用动作、演示状态、当前图层 | 执行动作后的页栈与数据 |
| 图与手机 `view.js` | 同一模型和会话 | 上下游、连线、可点的按钮与选中页面 |
| 影响分析与走查 | 需求关联、可到达的入口和导航规则 | 可执行的动作序列与可观察结果 |
| 依据页 `evidence.html` | 示例需求说明和状态 | 图上能打开的原文位置 |

## 图和导航各自记住什么

关系图记住选中节点、展开方向、深度和视口。进入详情时，同一张图重新以详情为中心，把上游排左边，下游排右边。遇到来回跳转时，用方向和访问记录限制重复展开。两个页面之间如果同时有“保存”和“取消”，线可以合并，动作明细需要保留两条。缩放和平移应只改变视口。

导航记住用户实际按过的动作。同页操作改变预览状态；打开新页入栈；普通返回按历史出栈。示例用 `$self`、`$back` 表示同页与返回这两类特殊去向。实际产品若支持返回某一级、切换标签重置栈、系统中断，按它自己的导航语义扩展执行器。图上“定位某页”可使用可达路径建立预览上下文，与用户在 App 内真实返回分开处理。

## 需求怎么进入地图

页面、动作可以分别关联需求。一条动作能同时受多个需求约束。需求状态来自需求或验收记录；规划动作和规划节点只在规划图层里供推演。对多阶段需求，已交付部分进入现状，剩余操作继续留在规划层。需求正文、状态依据、开发记录可以分别指向仓库内的固定文件或段落。

只有页面级的依据时，应把推导的动作标为“页面相关”。在完整应用里，多个来源可能共用系统分享面板。影响分析要结合“从哪个入口进入、分享的是什么”，逐步扩大范围。候选路径尽量覆盖不同来源、状态变化和退出方式，避免把所有可能的点击排列一遍。

## 走查结果怎么算

一步走查应同时知道当前上下文、用户点的动作，以及动作结束后要看到的页面或状态。“完成分享”和“取消分享”即使都回到预览，也不能相互抵扣。演示需要在开始时保存原浏览现场，退出后还原。额外验证落在用户能看见的结果上，例如取消编辑保留旧笔记，保存后返回详情能看到新笔记。

## 扩展到自己的产品

新增页面时先接真实入口，再补退出、取消、失败和重试等实际存在的分支。先用一条完整流程验证数据结构，再扩到全应用。为了支持页面搜索、全局图、分类图标、截图对照、灵感留档或多方案叠加，可以增加视图和索引，让它们继续读取同一套稳定 ID。将模型、示例资源和需求依据随应用纳入版本管理，检出旧提交就能重现当时的地图。
